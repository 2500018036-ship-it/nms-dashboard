# THEAZ centralized access — audit and deployment boundary

Audit performed on 27 October 2026 using read-only SSH, routes, process/resource inspection and bounded unauthenticated HTTP requests. No WireGuard, routing, firewall, device settings or running service configuration was changed for this audit.

## Existing path

`Client HTTPS → 20.194.8.143 Nginx → wg0 (source 10.10.0.1) → 192.168.20.195 NPM → nms-dashboard → nms-bot`.

The gateway already routes `192.168.20.195` over WireGuard and has a recent handshake. The web server reaches management VLANs through `192.168.20.1`. No client VPN, additional WireGuard peer, new public port or routing/firewall change is required for the proposed portal.

NMS has opaque server sessions with revocation and account revisions, Secure/HttpOnly/SameSite=Strict cookies, role permissions and a persistent audit table. GUI vault metadata exists only for the TP-Link integration. Collector credentials are not GUI credentials and will not be reused automatically.

The web server has two CPUs and approximately 3.8 GiB RAM (about 2.2 GiB available during the audit). The gateway has approximately 0.8 GiB RAM. Browser sessions belong on the web server. The initial deployment is limited to one active browser session globally, at most 1 GiB browser memory, an idle timeout and an absolute lifetime.

## GUI reachability and compatibility

| GUI | Audited endpoint | Result | Embedding / transport finding |
|---|---|---|---|
| MikroTik | `http://192.168.20.1/` | 200 RouterOS | X-Frame-Options SAMEORIGIN; root-relative assets. HTTPS port unavailable. |
| Cisco SF200 | `http://192.168.10.26/` | 302 | Absolute redirect to its private IP and versioned root. HTTPS port unavailable. |
| TP-Link TLWR | `http://192.168.10.194/` | 200 | Native JavaScript/encryption UI; current address follows its registered MAC. HTTPS port unavailable. |
| Proxmox | `https://192.168.20.200:8006/` | 200 | TLS verifies with the existing internal CA. Native console needs WebSocket. |
| Technitium DNS | `http://192.168.20.199:5380/` | 200 | X-Frame-Options DENY and CSP frame-ancestors 'none'. |
| Portainer | `https://192.168.20.195:9443/` | 200 | Self-signed TLS; CSP frame-ancestors 'none'. Explicit certificate trust is required. |
| Nginx Proxy Manager | `http://192.168.20.195:81/` | 200 | Root-relative assets; independent authentication. |

Directly placing these origins under same-origin iframe paths would require incompatible URL rewrites, cookie handling and removal of application security headers. It would also run device JavaScript in the NMS security origin. The approved approach is an isolated server-side browser whose native GUI is rendered inside the NMS content area. GUI HTML/JavaScript, cookies, redirects and native WebSocket traffic remain inside that browser; NMS receives the display stream and sends input.

The current gateway and NPM location do not forward Upgrade/Connection for WebSocket. Their proposed `/access-api/` locations therefore need a narrow, explicit configuration change. These changes are staged for review and are not activated without the user's permission.

## Isolation design

- A new gateway validates the existing NMS session and device ACL before creation and before each display connection; active sessions are revalidated periodically and stopped on expiry/revocation.
- One ephemeral browser container per session, no published ports, `network=none`, non-root, read-only root filesystem, dropped capabilities and private profile. No Docker socket, NMS database or credentials are mounted in browsers.
- Browsers reach only their selected audited origin through a per-session Unix socket and an allowlisted HTTP/CONNECT proxy. Their network namespace has no external interface. Upstream HTTPS is not intercepted.
- A separate root-owned Unix-socket broker can create/stop only the fixed browser image with fixed limits and the portal's labels. The HTTP gateway has no direct Docker socket.
- Proxmox/Portainer certificate trust is explicit and specific; there is no blanket TLS verification bypass. Their observed SPKI pins are recorded in the target configuration for review before activation.
- Native GUI login remains required. Browser profiles and GUI cookies are removed with the session. Credentials, input, clipboard, pixels and GUI response bodies are never written to audit logs.
- Audit events cover actor, target, session lifecycle, authorization failure and termination reason. Device administration remains subject to the native device account permissions.

## Activation requires approval

The prepared deployment changes only the NMS application images, adds the access gateway and constrained broker/browser runtime, and adds `/access-api/` WebSocket locations to the existing NMS virtual hosts at gateway and NPM. It does not change WireGuard, LAN/VLAN routes, firewall rules or target-device services. Device GUI endpoints remain private.

Authenticated native login/console tests need the corresponding native GUI accounts. The audit establishes reachability and headers, not successful administrative login. GUI-specific operations such as VM consoles, uploads and downloads must be recorded separately as tested or untested.
