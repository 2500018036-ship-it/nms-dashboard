## P0 — Stabilitas AI dan Telegram

1. **Penyebab ditemukan:** traceback awal berhenti di `status_message.edit_text` dengan `telegram.error.TimedOut`, sesudah AI selesai. Handler lama memasukkan kegagalan Telegram ke kategori “Permintaan AI gagal”. Request Telegram biasa memakai timeout default 5 detik. OpenRouter key valid, pertanyaan umum berhasil, dan tool call berhasil pada audit. Penyebab gangguan upstream Telegram yang sesekali lambat belum dapat dipastikan; tidak ada bukti API key tidak valid.
2. **File berubah:** `bot.py`, `app/config.py`, `app/main.py`, `app/logging_config.py`, `app/ai/{client,agent,tool_registry,prompts}.py`, `app/telegram/{handlers,formatting}.py`, `requirements.txt`, `Dockerfile`, `compose.yaml`, ignore files dan pengujian.
3. **Hasil implementasi:** async client; klasifikasi auth/quota/rate-limit/model/network/timeout/server/protocol; retry satu kali terbatas untuk error transient; fallback eksplisit; respons kosong/terpotong ditolak; maksimal tiga putaran tool dan satu final; deadline 150 detik. Tool memakai JSON schema ketat, unknown tool ditolak, target tidak menerima URL/IP bebas. Jawaban umum dan monitoring dipisahkan. Hasil seluruh tool UNKNOWN ditampilkan deterministik tanpa angka karangan. Secret disaring dari log, hasil tool dan Telegram. Pesan panjang dipecah berdasarkan unit UTF-16.
4. **Perintah/tes:** Docker test stage, unittest tanpa jaringan/secret, kompilasi seluruh Python dengan `compile`, pemeriksaan sintaks JS dengan `node --check`, smoke live OpenRouter dan DNS, Telegram `getMe`, send/edit.
5. **Hasil aktual:** suite final **61/61 lulus dalam 13,263 detik**. Pertanyaan umum menghasilkan jawaban; agent memilih `check_service` untuk DNS, query aktual berhasil, lalu jawaban Bahasa Indonesia diterima. Telegram send/edit berhasil pada pesan ID 41. Kandidat `poolside/laguna-s-2.1:free` gagal HTTP 404 ketika dipakai langsung dengan persyaratan tool; tidak dikonfigurasi sebagai fallback. `nvidia/nemotron-3.5-lightning:free` berhasil satu alur DNS lengkap secara langsung dan menjadi fallback eksplisit. Failover ketika primary error diuji dengan mock; tidak memaksakan gangguan provider produksi.
6. **Deployment:** service NMS dibangun dan direcreate sendiri dengan `up -d --no-deps --no-build`. Verifikasi final health dicatat pada bagian akhir laporan.
7. **Dampak layanan lain:** ID dan StartedAt seluruh container lama selain NMS cocok dengan baseline; tidak ada recreate/restart aplikasi lain. Tidak ada perubahan router atau Proxmox.
8. **Keterbatasan:** free model tetap bergantung pada ketersediaan/kuota provider. Pengiriman API sudah diuji dan pengguna telah mengonfirmasi bot membalas pengujian pesan masuk dari akun manusia. Bot tidak menyimpan percakapan permanen.
9. **Langkah berikut:** gunakan `/diagnostics` dan contoh percakapan pada README; ukur gangguan Telegram lebih lanjut bila timeout jaringan muncul kembali.

Tambahan yang ditemukan saat rollout: PTB 22.5 menandai `Bot._initialized` sebelum `getMe` selesai. Bila bootstrap pertama timeout lalu dicoba ulang, identitas bot dapat masih kosong; rollout awal sempat restart satu kali. Hook startup kini memverifikasi `getMe` sebelum membuat task, health menilai poller benar-benar berjalan, dan cleanup juga dipanggil pada jalur startup gagal. Dua tes lifecycle memeriksa kasus ini. Query system/interface MikroTik diserialisasi agar satu tidak selalu kalah oleh lock collector saat pemeriksaan paralel.

2. **File:** `app/monitoring/{common,tcp,dns,web,mikrotik,proxmox,docker_monitor}.py`, `app/services/health.py`, `deploy/host_collector.py`, unit systemd dan tes collector.
3. **Fitur:** status seragam UP/DEGRADED/DOWN/UNKNOWN dengan metode dan timestamp; cache 60 detik; DNS A aktual; HTTP streaming tanpa mengikuti redirect dan dengan verifikasi TLS; RouterOS field minimum dan pemeriksaan permission; PVE read-only GET; snapshot Docker dan Debian dari collector root yang terpisah.
4. **Perintah:** probe di container, baca konfigurasi server_name Nginx Proxy Manager, install/start `nms-collector.service` dan timer, mock collector serta allowlist security test.
5. **Hasil aktual:** DNS Technitium menyelesaikan `example.com`. Domain cloud HTTPS merespons 302; portfolio 200; HTTP host 200. Docker daemon dapat dibaca, CPU/RAM/storage Debian tersedia. Proxmox TLS tidak dipercaya dan menjadi UNKNOWN. Akun MikroTik lama memakai grup bawaan `read` yang juga mengizinkan reboot/password/sensitive; API monitoring diblokir sampai akun minimum tersedia. Sampel audit awal RouterOS: 7.19.5, hAP lite, CPU 100%; angka itu satu sampel, bukan status terkini.
6. **Deployment:** host collector terpasang sebagai root-owned script dengan endpoint/method GET yang dibatasi kode, tanpa listener jaringan. Timer sekali per menit. Bot menerima bind mount snapshot read-only; Docker socket tidak dimount.
7. **Dampak:** tidak ada akses exec/create/start/stop Docker melalui agent, tidak ada perubahan layanan/router/VM.
8. **Status:** DNS/web/Docker/host selesai dan teruji live. MikroTik dan PVE diimplementasikan, diuji mock, **terhambat akun/token/CA** untuk penggunaan penuh. DHCP/route/VLAN sengaja nonaktif secara default. Login/upload cloud dan transaksi SQL aplikasi belum diuji; health database yang terlihat berasal dari healthcheck container.
9. **Berikutnya:** akun RouterOS `read,api` saja; token PVEAuditor terpisah dengan CA tepercaya, expected guest VMID dan allowlist interface penting. User mengonfirmasi token PVE belum ada dan akan diberikan kemudian.

Docker juga menampilkan empat container restore-check yang sudah exited sebelum audit. Daftar pengecualian alert memakai empat nama persis dari baseline, tanpa wildcard; status tetap ditampilkan. Ini mencegah job maintenance yang memang berhenti dinilai sebagai gangguan baru. Container lain tetap diawasi.

## P2 — Riwayat dan alert

1. **Masalah:** belum ada penyimpanan hasil, alert state, retensi atau scheduler.
2. **File:** `app/storage/database.py`, `app/alerts/engine.py`, `app/services/scheduler.py`, integrasi lifecycle dan tests.
3. **Fitur:** SQLite WAL dengan synchronous NORMAL dan busy timeout; hasil/check, state alert, event/recovery, metadata; retensi 30 hari; cleanup harian; scheduler tunggal dengan lock proses; polling 180 detik tanpa completion AI. Threshold CPU/RAM/storage 90%, hysteresis 5 poin, dua sampel gagal/baik, dedup, cooldown 3600 detik dan retry pending notification. UNKNOWN tidak menjadi recovery. Counter restart dibandingkan dalam jendela 15 menit. Daily summary tersedia tetapi nonaktif.
4. **Tes:** dedup, restart engine, hysteresis, recovery, unknown, notifikasi gagal, cleanup dan pengecualian maintenance.
5. **Hasil:** unit test lulus dan siklus scheduler produksi menulis hasil ke SQLite. Tidak dilakukan fault injection destruktif pada router, aplikasi atau VM. Recovery incident penuh tidak diklaim teruji live hanya berdasarkan mock.
6. **Deployment:** volume `./data`, UID/GID 10001 mode 700. Alert diaktifkan untuk user allowlist yang sudah dikonfigurasi. Snapshot dan DB tidak menyimpan raw log, env atau percakapan.
7. **Dampak:** observasi saja; tidak ada auto-remediation atau restart layanan.
8. **Keterbatasan:** synchronous NORMAL menjaga atomicity, tetapi pemadaman listrik dapat kehilangan transaksi terbaru sebelum checkpoint WAL. Retensi menghapus record secara logis, tidak mengecilkan file DB setiap polling. Alert PVE/interface bergantung pada konfigurasi ekspektasi yang belum diberikan.
9. **Berikutnya:** evaluasi threshold dan interval sesudah riwayat nyata terkumpul; aktifkan ringkasan harian bila diperlukan.
